# MemGuard 参赛说明（中文稿）

> 本文用于整理“其他人工智能应用”赛道的作品介绍、评审问题答复和答辩口径。技术能力描述以当前比赛仓库为准；网页端使用固定脚本和合成数据，不代表已接入真实客户系统或在线大模型。

## 一、作品定位与核心差异

### 一句话定位

**MemGuard 是面向 AI Agent 长期记忆的治理与证据层：在记忆进入上下文、影响回答或跨团队流转时，记录其来源、版本、有效期、归属和策略决策，并让输出可以回溯到证据。**

它要回答的不是“模型这次调用发生了什么”，而是：**Agent 为什么能看到并使用这条记忆？这条记忆现在仍然有效吗？它支持了回答中的哪项事实？如果来源或策略更新，哪些历史输出需要复查？哪些记忆可以交给下一个 Agent？**

### 与 LangSmith 的边界：互补，而不是换皮竞品

两者都可能展示 Trace、评估或调试信息，因此演示时要从“治理对象”和“决策时点”讲清楚差异，不要只说“我们也有溯源/监控”。LangSmith 官方文档介绍了对 LLM 应用运行过程进行 tracing，以及基于数据集的离线评估、线上评估和回归比较；MemGuard 的参赛重点则是**Agent Memory 的生命周期与证据准入治理**。[LangSmith evaluation types](https://docs.langchain.com/langsmith/evaluation-types) · [LangSmith online evaluators](https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge)

| 维度 | LangSmith（按其官方文档概括） | MemGuard 的参赛定位 |
| --- | --- | --- |
| 主要观察对象 | LLM 应用运行、Trace、数据集评估和线上质量反馈 | Agent 读取、使用、更新、拒绝或交接的长期记忆及其来源证据 |
| 核心问题 | 一次应用运行经历了什么？输出质量如何？版本是否回归？ | 哪条记忆影响了回答？来源和版本是否有效？策略是否允许它进入上下文？ |
| 主要治理时点 | 运行可观测、评估与迭代环节 | 记忆被检索/纳入上下文之前，以及输出归因、来源更新和记忆交接时 |
| 参赛作品可展示的闭环 | Trace/输出检查 | 来源版本 → 记忆事件 → 输出证据 → 策略判定 → 调查案例 → 影响分析/重放；并展示记忆交接边界 |

这不是对 LangSmith 全部能力的穷举，也不主张 LangSmith 缺少某项具体功能。准确的答辩表述是：**LangSmith 可以承担应用运行可观测与评估；MemGuard 聚焦于长期记忆本身的来源、时效、归属、准入和跨任务治理。两者可在同一 AI 系统中互补。**如果某次 Agent 调用同时产生运行 Trace 和记忆证据，前者记录执行过程，后者解释记忆为什么可被使用、使用后影响了什么。

### 护城河：不是一个仪表盘，而是可累积的治理闭环

1. **记忆级证据链。** 将来源/版本、记忆事件、决策 Trace、输出和治理理由关联起来，目标是把“模型答得像不像对”进一步拆解为可检查的问题：记忆从哪来、何时有效、经过了什么策略、进入了哪段输出。当前代码提供事件、Trace、调查和证据展示组件；比赛网页用固定数据演示该交互。
2. **时间与来源变更意识。** 旧政策、过期记忆和新版本可能同时存在。仅保存一个最终答案不足以解释当时使用了什么，也不足以发现新来源到来后应复查哪些结果。仓库中的调查示例演示来源版本影响查询、补充证据和确定性重放。
3. **治理状态可区分。** 记忆不只是“保留/删除”：示例区分可用、已使用、过期/拒绝、待人工审核、保留在权威源、可转移、受保护、脱敏审核和归档，便于企业将责任与数据边界放入 Agent 工作流。
4. **系统与模型解耦的产品方向。** SDK 的事件/传输抽象和证据层定位意在接入不同 Agent、记忆存储和模型栈，而不把产品价值绑定于单一模型供应商或聊天 UI。当前比赛仓库展示了 SDK/后端代码和离线 Web Demo；大规模多租户部署、生产级连接器、吞吐/延迟指标及商业客户验证不应被表述为已完成能力。
5. **可积累的组织治理资产。** 长期价值来自组织逐步沉淀的来源目录、版本规则、记忆所有权、策略、拒绝/审核原因和复盘案例。它们将形成更可靠的接入映射与治理流程；这是产品的护城河假设和建设方向，不是本次静态 Demo 已经证明的网络效应或市场壁垒。

**答辩短句：**“LangSmith 主要帮助团队观察和评估 Agent/LLM 的运行；MemGuard 管的是运行中被读取的长期记忆：它从哪里来、是否过期、能否进入上下文、影响了哪条回答，以及更新后哪些输出要复查。我们关注记忆数据层的治理，可以与 LangSmith 等运行可观测工具并用。”

## 二、按评分标准组织展示

### 1. 作品选题与定位（30 分）

- **新颖性：** 从“模型生成文本”前移到“记忆如何进入 Agent 决策”，聚焦来源、版本、时效、归属及证据准入；强调与运行 Trace/输出评估的互补边界。
- **针对性：** 长期记忆会累积过期政策、互相矛盾的事实、缺乏来源的摘要，以及不应跨用户/团队传递的内容。作品以客服退款和员工离职交接两个具体场景展示这些风险。
- **落地性：** 用 SDK 事件/Trace、后端调查能力和浏览器端证据控制台构成可检查的技术路径；可先在高风险客服或企业知识 Agent 中接入只读来源和人工审核，不必一开始自动执行业务动作。
- **痛点证据口径：** 不用未经验证的市场规模或客户数据。答辩展示可复现的失效样例：旧版退款规则、过期 30 天例外、缺少治理元数据的摘要；再展示拒绝/人工审核/重放如何降低错误沿用风险。

### 2. 技术方案与实现（35 分）

架构按职责分层：

1. **SDK/事件采集层：** 记录 Agent、会话、记忆键、操作、来源/版本、内容摘要标识及时间等事件，并保留传输和回放抽象。
2. **后端证据与调查层：** 保存记忆事件和决策 Trace，关联输入记忆与输出；支持调查案例、来源版本影响查询和重放记录。具体接口及完成范围以仓库代码、测试为准。
3. **治理决策层：** 用有效期、来源状态、所有权和策略结果表达“允许、拒绝、只读保留、待审核、脱敏/保护、归档”等不同处置，而非仅显示一个笼统分数。
4. **展示层：** Evidence Console 讲解输出—记忆—证据—治理理由；Agent 页面将来源 chip 内联到回答并可打开 Trust/Policy/Source 详情；Handover 页面呈现记忆是否到达 successor 的边界。
5. **调查闭环：** 新来源版本到来后查询已知影响，形成调查案例，用确定性示例重放变体并记录结果，便于审查修复过程。

**可靠性与诚实边界：** 当前比赛 Web Demo 是离线固定逻辑、合成数据；Python 示例中的 Agent 输出亦为本地确定性函数。演示中的 trust 数值是 UI 样例元数据，不是经过校准的正确率概率。不得把离线模拟说成真实 LLM 推理、生产数据接入或自动退款。

### 3. 功能效果与价值（20 分）

- **可见效果：** 评委可以从某条客服回答点击来源 chip，检查事实依据、信任标签、策略、来源 ID 和是否进入回答上下文；也能在 Evidence Console 看到过期记忆被排除，以及在 Handover 看到个人/混合/陈旧记忆的处置边界。
- **应用价值：** 减少过期或无来源记忆被长期沿用的风险；缩短事故调查时定位相关记忆/来源版本的路径；在人员或 Agent 更替时保留公司知识，同时限制私人或未审核信息的传播。
- **效果指标设计（后续接入真实场景后测量）：** 证据覆盖率、来源版本可追溯率、过期记忆拦截率、错误记忆导致的回答占比、调查定位时长、重放复现率、未授权交接拦截率、人工审核命中与误报率。比赛 Demo 目前只展示流程，不声称这些指标已在生产环境达成。

### 4. 作品呈现与答辩（15 分）

建议演示顺序：**先看 Agent 回答和绿色来源 chip → 打开 Memory evidence 弹窗 → 跳到 Evidence Console 检查证据故事及过期记忆 → 打开 Handover 选择一条受保护/转移记录 → 用 Python 示例补充来源版本影响和确定性重放。**

讲解时明确每个页面的静态/动态边界、合成资料和“无外部业务写入”说明；避免先讲抽象架构或把 trust score 当模型正确率。提交物应包含产品说明、安装说明、设计思路、设计重点难点、代码及可访问演示入口。

## 三、评审问题答复稿

### 问题 1：开源代码与组件使用情况说明

**答复：**本作品提交代码位于比赛专用仓库，包含 Python SDK、后端服务/调查组件、确定性示例、测试，以及独立的 Next.js 离线演示前端。SDK 定义记忆事件、影响信息、传输和重放等基础接口；后端代码提供事件/Trace 存储、审计、调查与迁移相关模块；Web Demo 展示客服回答的证据来源、策略状态和企业记忆交接。

比赛 Demo 的回答逻辑和记录为仓库内合成示例，不使用商业 API key、客户数据或外部模型服务。Python SDK 的 `sdk/pyproject.toml` 声明项目元数据及 MIT license 字段；依赖组件分别以 `backend/requirements.txt`、`sdk/pyproject.toml`、`vercel-demo/package.json` 管理。**不要据此将仓库所有代码或每个依赖概括为 MIT**；若提交平台要求逐项开源许可证清单，应按实际提交版本补充依赖名称、版本及其上游许可证，并核对仓库根目录的许可证文件状态。

### 问题 2：作品安装说明

**答复：**评委无需配置模型服务即可体验在线演示：访问 [MemGuard Competition Demo](https://mem-guard-competition-2026.vercel.app/)，从 Evidence Console、Support Agent 和 Enterprise Handover 三个页面操作。离线运行方式、命令、Python 示例和测试见 [`README.md`](../README.md) 与 [`USER_GUIDE.md`](USER_GUIDE.md)。网页 Demo 需要 Node.js/npm 安装依赖；Python 调查示例需要 Python 环境及 `backend/requirements.txt`、`sdk/pyproject.toml` 中列出的依赖。当前离线体验无需 API key、`.env`、数据库账号或身份认证配置。

安装后可依次检查：

1. Agent 页面初始回答和 `ORD-4821` 的 inline source chip；
2. `I need a refund for ORD-4821 because the item is defective.` 的人工审核模拟；
3. Evidence Console 的输出、证据、过期记忆及事件视图；
4. Handover 页面中保留源系统、可转移、个人保护、脱敏待审核和归档样例；
5. Python 示例中的 evidence completeness、source impact、replay 与 case status 输出。

### 问题 3：设计思路

**答复：**我们从一个 Agent 记忆治理问题出发：模型输出即使语言流畅，也可能使用旧规则、失效例外、没有来源的摘要或不属于当前用户/组织的记忆。单看最终回答或调用 Trace，未必能回答“当时检索了什么、为什么允许它进入上下文、它支持了哪项主张、来源更新后哪些输出要复查”。

因此把系统设计成记忆侧的证据闭环：SDK 捕获记忆读写事件及其来源元数据；后端将事件与决策 Trace 关联；治理状态保留来源版本、有效性、所有权和处置理由；调查能力围绕旧输出建立案例、查询受影响结果并记录重放；前端将来源证据直接呈现在回答旁，并把组织记忆跨 Agent 交接中的可转移/不可转移理由可视化。

和 LangSmith 的区别不是“有没有 Trace 界面”，而是治理对象不同：LangSmith 的官方材料覆盖应用 tracing 与评估工作流；MemGuard 以记忆记录及其在上下文中的准入/影响为核心，可作为这些工具旁边的 memory governance 层，而不替代通用运行可观测、数据集评估或模型实验平台。

### 问题 4：设计重点与难点

**答复：**

1. **把输出主张与具体记忆证据关联。** 一条回答可能混合订单事实与政策约束；设计上必须区分 factual support、policy constraint 和 rejected context，避免让“某条记忆出现过”被误解为“它支持所有输出”。
2. **处理时间和版本。** 来源更新并不应抹去旧输出在当时依据的证据；需要同时保留历史版本关联并能查询新版本出现后需要复查的已知输出。
3. **区分置信信息与事实正确率。** trust 只能表达某种来源/治理元数据或样例评估状态，不能不加校准地宣称是答案正确概率。演示中因此解释 trust 标签是合成样例。
4. **在拒绝、保护和交接间做细粒度处置。** 过期、无来源、私人、混合内容和权威公司来源的处理方式不同；简单的“全部复制/全部删除”无法满足企业连续性和边界要求。
5. **让演示可复现又不误导。** 评委可本地运行固定答案、源版本影响和重放用例，无需泄漏商业 API key；同时必须明确固定脚本、合成数据与生产接入之间的差异。
6. **与运行可观测工具划清边界。** 若只展示一张 trace 页面，容易被误认为 LangSmith 类产品。因此演示要始终从记忆的来源/时效/准入/归属/交接讲起，trace 是连接证据和输出的载体，而不是产品定位本身。

## 四、现场演示建议

1. 打开 `/agent`，说明“固定合成客服例子，不调用模型或退款接口”。
2. 点击回答中 `support order db` 标签，展示 `Role in output / Trust / Policy / Source / Included in prompt` 和完整证据入口。
3. 提交缺陷退款场景，指出政策要求人工审核，强调没有真实退款写入。
4. 打开 Evidence Console，展示过期例外被拒绝、证据故事及相关记忆事件。
5. 打开 `/handover`，分别选择公司知识、私人记忆和混合内容，解释留源、转移、保护、审核/脱敏或归档边界。
6. 如评委询问工程闭环，运行 `examples/investigation_demo.py`，讲解来源版本影响查询和确定性重放；最后指出生产化下一步是连接真实记忆源、策略配置、权限审计和效果指标验证。
